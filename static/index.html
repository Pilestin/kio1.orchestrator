Planning model

Producing a valid plan means following the rules in the system prompt: pick a registered capability, order the steps, declare what depends on what. That is hard for a small model, and the failure is not an error message — it is a plausible-looking plan in the wrong order. If a run fails for a reason that reads like a missing prerequisite, try a larger model before changing anything else.

How to use

What a target is, how a request becomes a plan, and what to write in the box on the Targets tab.

How a request becomes a plan

The box on the Run tab is not a chat with an agent. What you write goes to the planning model, once, together with a generated catalog of every usable target and the rules in the system prompt. The model answers with JSON: a list of steps, each naming a target and one of its capabilities.

KIO1 then dispatches that plan. It does not interpret your words any further — the plan is all it has. Three things follow from that, and they are where most failed runs come from:

  1. A capability the catalog does not list cannot be asked for. If nothing registered provides what you want, the model is told to leave it out rather than invent a target.
  2. The model decides the order. A step that needs the output of another must declare it. A small model routinely gets this wrong, and the result is a step that runs before the thing it depends on has produced anything.
  3. Code you paste into the box is not sent to an agent. It becomes part of the request the model reads. The code an agent analyses comes from the workspace on the Settings tab, which travels in every message.

So a request that names what you want in the catalog’s own words works better than one that describes it. Ask to localize the failure rather than to get the trace, when localization is the capability that produces a trace.

Plugging in your own agent

KIO1 dispatches to targets. A target is anything that can carry out a step: a KIO agent, an ordinary REST API of yours, or a program on the machine this service runs on. It does not have to know KIO1 exists.

What a plan actually asks for is a capability — the agent name in it is only the planner's guess at who provides one. So the two things every target must declare are the capabilities it offers and a description the planner can read when deciding whether it fits.

Adding one is the Targets tab. Paste a definition, press Add. It is probed straight away, and by default written into the configuration file so it is still there after a restart. You never have to edit code.

The three kinds

kio — a service speaking the KIO1–KIO10 protocol

It accepts an execution message at one path and answers in the agreed shape. This is the default when no type is given.

{
  "agent_id": "KIO7",
  "description": "Code generation and code understanding.",
  "endpoint": "http://127.0.0.1:8107",
  "path": "/execute",
  "capabilities": ["code_generation", "code_understanding"]
}

http — any REST API

The request is built from a template, so an API that knows nothing about KIO1 still works. Omit body and the standard execution message is sent instead. result_path picks the part of the response worth keeping; health_url lets it be probed.

{
  "agent_id": "LogSearch",
  "type": "http",
  "description": "Searches the internal log index for a pattern.",
  "url": "https://logs.internal/api/v1/search",
  "method": "POST",
  "headers": {"Authorization": "Bearer ${LOG_API_TOKEN}"},
  "body": {"query": "{task}", "repo": "{data.repository.path}"},
  "result_path": ["report"],
  "health_url": "https://logs.internal/healthz",
  "capabilities": ["log_search"]
}

cli — a program on this machine

The command is a list, and it runs with no shell involved: a task description containing ; or quotes becomes one argument and stays one argument. Exit code 0 succeeds. If it prints a JSON object, that object becomes the step's output — which is how a local tool reports verdict like any agent.

{
  "agent_id": "Pytest",
  "type": "cli",
  "description": "Runs the project's test suite and reports what failed.",
  "command": ["python", "-m", "pytest", "-q", "{data.repository.path}"],
  "cwd": "",
  "capabilities": ["test_execution"]
}

mcp — a server that describes itself

The only kind you do not have to describe. A Model Context Protocol server is asked what tools it has, and the answer — names, descriptions, and the exact arguments of each — becomes this entry's capabilities. Nothing about them is typed here, and nothing goes stale when the server changes. There is a large ecosystem of these already written, and any of them is three lines away from being a workflow target.

{
  "agent_id": "Workspace",
  "type": "mcp",
  "description": "Reads and writes files in the workspace.",
  "command": ["npx", "-y", "@modelcontextprotocol/server-filesystem", "/work"]
}

Use command for a server KIO1 starts here, or url (with headers) for a remote one — one or the other, never both. On Windows an npm-published server needs npx.cmd, because the command runs without a shell. In a container, the program has to be in the image.

A tool's name is the capability value. Press Test connection to see the list before you save; adding capabilities turns it into an allow-list, so a server that can also write can be registered read-only.

An MCP tool takes named arguments rather than prose, so a plan step addressed to one may carry an arguments object — the planner fills it in from the schemas it was shown. Where a tool needs exactly one string, the step's task is used as that string. Where it needs more and the plan gave none, the step fails saying what was missing rather than inventing a value for a tool that writes files.

Placeholders

Anything in url, headers, body, command and env can carry these. A string that is exactly one placeholder keeps the value's type, so "{data}" sends an object. A name that is not a known field is left alone, so a typo shows up in the request instead of quietly blanking a field.

PlaceholderValue
{task}The step's instruction from the plan
{capability}What the step asked for
{workflow_id}, {step_id}, {agent_id}Step identity
{data}The whole structured input
{data.repository.path}The code under analysis
{data.upstream.s1}What step s1 returned
${ENV_VAR}Read from the server's environment — keeps credentials out of the file

Letting an agent register itself

Pasting a definition is the manual path. If your service can serve one more URL, it can describe itself and skip this form entirely — publish a manifest and point KIO1 at it, or push it to the registry API:

curl -X POST http://localhost:8000/registry/agents \
  -H "Authorization: Bearer $KIO1_REGISTRY_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"manifest": {"agent_id": "MyAgent",
                    "description": "What it does.",
                    "endpoint": "http://10.0.0.5:9000",
                    "capabilities": ["my_capability"]}}'

The smallest useful manifest is three fields — agent_id, description, capabilities. Leave the address out and KIO1 uses the one it fetched the manifest from, which is the one address a manifest cannot get wrong.

Before you add it: Test connection

Test connection checks an entry without adding it. It tells you what it understood, which address it actually dialled, and whether that address answered.

The middle one matters because it is not always what you typed. A deployment can redirect addresses with KIO1_AGENT_HOST or KIO1_AGENT_ENDPOINT_<AGENT>, and when it does, the result says so:

You wrote http://127.0.0.1:11434/, and this deployment dials
http://host.docker.internal:11434/ instead (KIO1_AGENT_HOST).

Only addresses meaning this machine — 127.0.0.1, localhost, 0.0.0.0, ::1 — are redirected that way. A public address such as https://api.open-meteo.com/… is dialled exactly as written.

A kio target is asked for its health path, an http tool for its health_url, and a cli tool is checked for its program being on this machine's PATH — so a CLI tool that lives on your laptop will not be found by KIO1 running in a container. Nothing is saved and nothing is run; a failed test does not stop you adding it.

What the statuses mean

Shows asMeans
readyProbed and answering
uncheckedNothing about it can be probed — an http entry with no health_url, for instance. Still used.
unreachableFailed its probe enough times to be withdrawn. It is not offered to the planner, and comes back on its own once it answers.
configIt is in the configuration file. Editing it here rewrites that file.
discoveryFound by fetching a manifest. Not written down unless you save it.
registrationPushed to the registry API without being saved. Gone at the next restart.

In a run's steps, ok means the call worked — not that it found nothing wrong. What it concluded is the separate verdict: clean, defect, or inconclusive. A step that says not_run was stopped: either a policy gate refused it, or something it depends on did not complete. The reason is printed beside it.

Where changes are saved

Adding, editing, or removing a target here rewrites the dispatch.agents section of the configuration file. Nothing else in it is touched, the write is atomic, and the previous contents are kept alongside as config.json.bak.

Untick Save to the configuration file to add something for this process only. On a deployment that ships a read-only configuration, set KIO1_CONFIG_WRITABLE=0; this console then says so rather than failing when you press Add.
